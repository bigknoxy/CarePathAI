# CarePath AI - Architecture Overview

This document describes the high-level architecture for CarePath AI, the AI-powered care journey assistant. It summarizes system components, data flows, security and observability considerations, and key architecture decisions.

## System Overview

CarePath AI is an end-to-end prototype that demonstrates using retrieval-augmented generation (RAG) and multi-step LLM orchestration to produce personalized care guidance from synthetic healthcare data. It is intentionally split into two primary layers:

- C# (.NET) Backend (CarePath.Api): authoritative API surface, orchestration, authentication/authorization, audit logging, background jobs, and integration points for observability and deployment.
- Python ML Service (CarePath.ML): embedding generation, vector store (FAISS), retrieval, prompt orchestration, safety guardrails, and LLM integrations.

A Blazor Server UI (CarePath.UI) provides a demo surface for interactive exploration of patient data and care path generation.

Explicit separation and RAG flow: The system uses C# (.NET) for orchestration and business logic (CarePath.Api) while Python (CarePath.ML) handles ML-specific tasks — embedding generation, retrieval from FAISS, and LLM prompt orchestration. For a given user request the orchestrator (CarePath.Api) issues a RAG call to CarePath.ML; the ML service retrieves relevant context from the FAISS index, runs the prompt chain to generate or augment content, applies safety guardrails (emergency detection, redaction, fallback responses), and returns the result to the API which records audit events and returns the response to the UI. Guardrails are implemented primarily in the ML service and are logged and audited by the orchestrator to ensure traceability.

```
[Blazor UI] <- HTTPS -> [CarePath.Api (.NET)] <- HTTP/gRPC -> [CarePath.ML (Python)]
                                    ↕
                                   [Postgres + pgvector]
                                    ↕
                                 [FAISS files on disk]
```

## Component Responsibilities

- CarePath.UI (Blazor Server)
  - Server-rendered UI for patient browsing and care path interactions
  - Calls CarePath.Api for all operations; no direct calls to ML service
  - Session-based authentication; keeps PHI on server side

- CarePath.Api (.NET)
  - REST API exposing patient endpoints, care path orchestration endpoints, admin endpoints
  - Services: PatientService, MLOrchestrator (calls Python), AuditService, BackgroundWorker
  - Middleware: Auth (JWT/OIDC stub), Request validation, Structured logging (Serilog), OpenTelemetry tracing

- CarePath.ML (Python FastAPI)
  - Endpoints: /embed, /retrieve, /orchestrate
  - Embeddings: sentence-transformers (all-MiniLM-L6-v2) local for self-contained demo
  - Vector DB: FAISS persisted to volume; optional pgvector for production discussion
  - Orchestration: simple LangChain-style pipeline or custom prompt chain; guardrails module for safety checks

- Data stores
  - PostgreSQL for structured metadata (users, patients, audits)
  - FAISS for vector retrieval persisted to disk
  - Synthetic data files under /data/synthetic

## Data Flow

1. Synthetic data generated by generator script and stored in data/synthetic
2. Python ingestion reads files, chunks notes, generates embeddings, and indexes FAISS
3. UI requests care path -> CarePath.Api retrieves patient metadata from Postgres -> calls ML service via MLOrchestrator
4. ML service retrieves relevant contexts from FAISS, applies prompt chain, runs guardrails, and returns result
5. CarePath.Api records audit, caches response, and returns to UI

## Observability

- Structured logs (JSON) from both .NET and Python services
- Metrics: /metrics endpoints for Prometheus scraping (requests, latency, errors, LLM calls, cache hit rate)
- Traces: OpenTelemetry spans across .NET and Python to visualize end-to-end request

## Security & Privacy

- Blazor Server keeps PHI on server-side rendering; avoid client-side leakage
- Auth: JWT-based auth with role checks for admin endpoints
- Secrets: env vars, .env.example in repo; CI/CD uses GitHub Actions secrets
- Logging: redaction rules for PHI before writing structured logs
- Guardrails: classify emergency content and enforce fallback message; log guardrail events for audit

## Deployment

- Local development: Docker Compose orchestrates UI, API, ML, Postgres, and optionally Prometheus/Grafana
- Small VPS: Docker Compose production file with nginx reverse proxy, TLS offload, external Postgres volume
- CI/CD: GitHub Actions for build/test; Actions deploy via SSH to VPS

## Key Trade-offs

- Using Blazor Server simplifies PHI handling and reduces client complexity at the cost of server state and scale concerns. Acceptable for a portfolio prototype.
- FAISS + sentence-transformers allows reproducible local demos without cloud costs, but is not a fully managed vector DB solution for heavy scale.
- Python ML service is separate to leverage ML ecosystem; this introduces cross-service complexity but demonstrates cross-stack integration skills.
